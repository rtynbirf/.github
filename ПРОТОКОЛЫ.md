# ПРОТОКОЛЫ · исполняемые процедуры дома

*Слой протоколов 2026-11-18. Протокол переводит статьи уставов (`УСТАВ-ЭМЕРДЖЕНТНЫЙ.md`)
в повторяемые шаги с гейтами. Каждый протокол имеет вход, шаги, выход и гейт отказа.
Семь протоколов выведены из мировых практик 2025–2026; восьмой — A-HUSH — рождён
в доме из вердикта «волна ×1176» (17.11.2026): 1176 красных прогонов за 8 дней оказались
честными тревогами на транзитную гонку такта, ни один страж не был сломан.*

---

## Протокол P-LOOP. Цикл «восприятие–действие»

**Назначение:** основной рабочий цикл одиночного агента. **Вход:** мандат с бюджетами.
**Выход:** результат с трейсом и обновлённой памятью. **Гейт:** любой бюджет исчерпан —
переход в H-HALT.

1. Развернуть мандат: цель, разрешённые инструменты, бюджеты, критерий успеха.
2. Восприятие: собрать контекст задачи; внешний контент — в карантин (У-3.2).
3. Планирование: построить план и сохранить его во внешнюю память (У-3.4).
4. Действие: выполнить один шаг плана через T-GRANT-проверенный инструмент.
5. Верификация: сверить результат шага с критерием; расхождение — коррекция плана,
   а не результата.
6. Запись: полный трейс шага (вход, выход, решение, стоимость) в журнал наблюдаемости.
7. Консолидация: обновить эпизодический слой памяти по M-OPS; вернуться к шагу 4 до
   достижения критерия успеха или гейта бюджета.

## Протокол E-GATE. Гейт публикации результата

**Назначение:** не выпускать заявление без доказательства. **Вход:** результат с черновым
заявлением. **Выход:** публикация со статусом зрелости и аудиторской цепочкой. **Гейт:**
отсутствие артефакта или верификатора — статус «незавершён».

1. Зафиксировать заявление в измеримой форме (что утверждается и в каких пределах).
2. Приложить артефакт: трейс, датасет, сборку, формальную проверку.
3. Прогнать независимый верификатор (второй процесс, другой контекст, формальный
   проверщик — У-2.3).
4. Собрать аудиторскую цепочку: кто, когда, чем проверял.
5. Назначить статус: проверено, прототип или незавершён; скрытие статуса запрещено (У-2.2).
6. Опубликовать только тройку «заявление — артефакт — верификатор» со статусом.

## Протокол M-OPS. Операции памяти

**Назначение:** поддерживать целостность четырёх слоёв памяти. **Вход:** поток событий
и внешнего контента. **Выход:** консолидированная, проверенная память. **Гейт:**
отрицательная проверка целостности — карантин слоя и инцидент ASI06.

1. Запись: каждое событие попадает в эпизодический слой с источником и меткой времени.
2. Карантин: внешний контент проверяется на внедрение инструкций до контакта
   с семантическим слоем.
3. Консолидация: повторяющиеся эпизоды сжимаются в семантические факты с указанием
   источников.
4. Забывание: устаревшие факты отзываются по версии, а не перезаписываются молча.
5. Проверка целостности: контрольные суммы и выборочная перепроверка фактов;
   расхождение — карантин слоя.
6. Упаковка: стабилизированные процедуры оформляются в Skills по прогрессивному
   раскрытию.

## Протокол T-GRANT. Выдача возможностей

**Назначение:** выдать инструмент минимально, адресно и с отзывом. **Вход:** шаг плана,
требующий инструмента. **Выход:** привязанный токен, отфильтрованный список возможностей.
**Гейт:** инструмент вне реестра — отказ и запись инцидента ASI04.

1. Запрос: шаг плана запрашивает инструмент с обоснованием.
2. Минимизация: из списка сервера отбираются только возможности, нужные шагу (У-4.2).
3. Выдача: токен с привязкой к серверу и сроком жизни; сквозная передача запрещена (У-4.1).
4. Сухой прогон: необратимый вызов сначала выполняется без реального эффекта (У-4.3).
5. Исполнение: вызов выполняется под полным трейсом.
6. Отзыв: токен отзывается по завершении шага или по таймеру, в зависимости от того,
   что наступит раньше.

## Протокол S-SYNC. Синхронизация роя

**Назначение:** детерминированная параллельная работа подагентов без взаимных помех.
**Вход:** задача оркестратору. **Выход:** синтезированный результат с сохранённым планом.
**Гейт:** превышение эшелона в пять воркеров — пересмотр декомпозиции.

1. Планирование: оркестратор строит план и сохраняет его во внешней памяти (У-3.4).
2. Декомпозиция: задача делится на независимые подзадачи с контрактами (цель, формат,
   границы, инструменты — У-5.1).
3. Эшелон: запуск трёх–пяти подагентов параллельно в чистых контекстах; правила
   масштабирования усилия в каждом брифинге (У-5.3).
4. Сбор: результаты возвращаются только в канонической форме; внеконкурсные форматы
   отклоняются.
5. Разрешение конфликтов: противоречия решаются верификатором E-GATE, а не голосованием
   уверенности.
6. Синтез: оркестратор сводит результат и решает, нужна ли вторая волна.

## Протокол H-HALT. Эскалация и безопасная остановка

**Назначение:** управляемый останов по бюджету, аномалии или требованию наблюдателя.
**Вход:** событие-триггер. **Выход:** снимок состояния и досье для человека. **Гейт:**
возобновление возможно только по явному решению человека.

1. Триггер: исчерпан бюджет (У-1.3), обнаружена аномалия цели (ASI01, ASI10) или получен
   внешний сигнал остановки.
2. Безопасный стоп: завершить атомарный шаг, не начинать новый; отозвать токены T-GRANT.
3. Снимок: зафиксировать план, память, открытые вопросы и последний трейс.
4. Досье: передать человеку краткое досье — что делалось, что найдено, что блокирует.
5. Возобновление: после решения человека агент продолжает со снимка, а не с нуля.

## Протокол R-AUD. Аудит репозитория-организма

**Назначение:** периодическая сверка роя репозиториев с уставами и реальностью.
**Вход:** инвентаризация репозиториев. **Выход:** отчёт аудита со статусами зрелости.
**Гейт:** расхождение описания и фактов — статус «незавершён» автоматически.

1. Инвентаризация: полный список репозиториев, языков, зависимостей и активных мандатов.
2. Сверка описаний: README и витрина сопоставляются с фактическим содержимым.
3. Верификация артефактов: выборочная проверка троек «заявление — артефакт —
   верификатор» (У-2).
4. Пометка зрелости: каждому репозиторию — статус проверено, прототип или незавершён.
5. Отчёт: сводка расхождений, инцидентов и назначенных исправлений; публикация по E-GATE.

## Протокол A-HUSH. Протокол тишины стражей (рождён в доме, волна ×1176)

**Назначение:** страж обязан молчать на транзитной гонке такта и кричать один раз при
настоящей поломке. **Вход:** красный или зелёный прогон стража. **Выход:** тишина (гонка)
или одна issue `alarm:*` (поломка). **Гейт:** отключение стража запрещено — это ампутация
иммунитета дома (вердикт совета агентов 2026-11-17: «стражи не сломаны — они дремуче
честны»).

1. **Грейс (зуб 1).** Перед тревогой страж перепроверяет факт 3 раза с паузой
   (90 с для пинов, 60 с для фасада/памяти/манифеста, 30 с для описания).
   Транзитный дрейф такта (пин, геном, фасад, описание догоняют пуш) — не тревога.
2. **Тревога однажды (зуб 2).** При честном красном надлого issue с меткой `alarm:<страж>`
   открывается **один раз**; пока она открыта — повторные красные молчат.
3. **Разоружение.** При зелёном такте страж сам закрывает свою `alarm:*` issue с
   факт-комментарием — предохранитель перезаряжается без человека.
4. **Место тревоги — issue, а не поток уведомлений.** Уведомления CI — шум; issue с
   меткой — адресный сигнал с историей.
5. **Ретрай записи.** Любой бот-пуш (самозапись, самозалечка) выполняется циклом
   `fetch → rebase → push` до 3 попыток: гонка ботов за main лечится повтором, а не
   красным.
6. **Откат протокола** — revert коммита с зубами; сам грейс не маскирует реальную
   поломку: после 3 перепроверок страж краснеет честно.
